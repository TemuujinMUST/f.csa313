## Алхам 2: Гурван сценарио бичих

| Хэсэг | Тайлбар |
|---|---|
| Тойм | Хэвийн ачаалалд сагсанд бараа нэмэх (`POST /cart/add`) хүсэлтийн хариу хугацааг шалгах |
| Системийн төлөв | Сервер хэвийн ачаалалтай: 20 зэрэгцээ хэрэглэгч (VU), ойролцоогоор 20 хүсэлт/секунд |

| Гадаад өдөөлт | Хэрэглэгч "сагсанд нэмэх" товч дарж `POST /cart/add` хүсэлт илгээнэ — 20 VU тогтмол ачаалалтайгаар 1 минутын турш |
| Шаардлагатай хариу | Сервер `{ ok: true, items: N }` гэж 200 OK буцаана; өгөгдлийн сан эсвэл гадаад дуудлага байхгүй |
| Хэмжүүр | Хүсэлтийн 95%-д хариу **20 мс**-ээс бага (20 VU тогтмол ачаалалд, 1 минут) |

| Хэсэг | Тайлбар |
|---|---|
| Тойм | Хэрэглэгчийн хэвийн төлбөрийн үйлдлийн үед `/pay` endpoint хэр олон удаа 500 алдаа буцаадгийг хэмжих |
| Системийн төлөв | Сервер хэвийн ачаалалтай (20 VU); хүсэлт бүр бие даасан |

| Гадаад өдөөлт | Хэрэглэгч захиалгаа баталгаажуулж `POST /pay` хүсэлт илгээнэ — 20 VU-аар 1 минутын турш |

| Хэмжүүр | Error rate (POFOD) **< 8%** (1 минутын цонхонд, 20 VU) |

### Availability сценарио — сервер эвдрэх ба сэргэх

| Хэсэг | Тайлбар |
|---|---|
| Тойм | Сервер гэнэт зогсоод 10 секундын дараа дахин асахад системийн бэлэн байдал хэрхэн өөрчлөгдөхийг хэмжих |
| Системийн төлөв | Тест эхлэхэд сервер хэвийн ажиллаж байгаа; 20 VU идэвхтэй хүсэлт илгээж байна |
| Орчны төлөв | Локал орчин; серверийн процессыг гараар зогсоож (Ctrl+C), 10 секунд хүлээгээд дахин асаана |
| Гадаад өдөөлт | **ЭВДРЭЛ (crash)** — сервер процесс зогсож, 10 секундын турш хариулахгүй болно |
| Шаардлагатай хариу | Зогсолтын үед хүсэлт бүр connection refused алдаагаар буцна; сервер дахин асахад шинэ хүсэлтүүд шууд 200 OK хариулж эхэлнэ |
| Хэмжүүр | 2 минутын цонхонд (10 секундын зогсолт орсон) бүх хүсэлтийн амжилтын хувь **≥ 90%**; сэргэх хугацаа **≤ 15 секунд** |

## Алхам 3: Сценарио бүрээс SLO гаргах

| Сценарио | SLI (юуг хэмжих) | Босго | Цонх / нөхцөл |
|---|---|---|---|
| Performance | `/cart/add` latency (p95) | **p95 < 20 мс** | 20 VU тогтмол ачаалалд, 1 мин |
| Reliability | `/pay` error rate | **< 8%** | 1 мин, 20 VU |
| Availability | Бүх хүсэлтийн амжилтын хувь (checks) | **≥ 90%** | 2 мин, 10с зогсолт орсон |

### Босго сонгосон үндэслэл

- **Performance (p95 < 20 мс):** Эхлээд `p(95)<200` гэж тавьсан байсан. Гэвч бодитоор хэмжихэд `/cart/add`-ийн p95 ердөө 1мс орчим гарсан (`results/pass.txt`) — `/cart/add` нь DB болон гадаад дуудлага хийдэггүй, шууд JSON буцаадаг тул үнэн хэрэгтээ 200мс хэзээ ч хүрэхгүй, өөрөөр хэлбэл юу ч шалгахгүй утга байлаа. Тиймээс бодит p95-аас ~20 дахин дээгүүр **20мс** болгож өөрчилсөн. Localhost дээр заримдаа cold-start/GC-ийн улмаас нэг хүсэлт 20-25мс хүртэл сунадаг тул тэр хэлбэлзлийг даван, харин өгөгдлийн сангийн дуудлага мэт жинхэнэ саатал нэмэгдвэл барих хэмжээний тоо.
- **Reliability (< 8%):** `/pay` дотор код нь `Math.random() < 0.05` гэж ~5% алдаа санаатай авсан. 8% гэдэг нь энэ 5%-аас арай өндөр (жижиг статистик хэлбэлзлийг тэвчих) боловч алдаа хоёр дахин их болвол (жишээ нь ~10%) FAIL болж мэдрэх түвшин.
- **Availability (≥ 90%, 2 мин, 10с зогсолт):** 120 секундийн цонхонд 10 секундийн зогсолт орвол хамгийн муу тохиолдолд ч availability ≈ (120−10)/120 ≈ 91.7% байх ёстой тооцоогоор. 90% босго нь энэ тооноос доор, өөрөөр хэлбэл chaos тест хэвийн явбал давах ёстой, гэхдээ бага зэргийн зай үлдээсэн тоо.

### Error budget тооцоо (Availability, ЦАГААР)

- SLO: 2 минутын (120 секунд) цонхонд availability ≥ 90%.
- Зөвшөөрөгдөх зогсолтын хугацаа = (1 − 0.90) × 120с = **12 секунд**.
- Энэ бол 2 минутын цонхонд системд байх "эвдрэх эрх" (error budget). Алхам 5-д төлөвлөсөн 10 секундийн зогсолт энэ 12 секундээс бага тул цагаар тооцвол SLO хангагдах ёстой.
- Энэ бол ЦАГААР тооцсон budget. k6-ийн `checks` метрик нь ХҮСЭЛТИЙН хувиар тооцогддог тул бодит гарах тоо өөр байж болно — сервер унасан үед хүсэлт агшин зуур (connection refused) буцдаг бол хэвийн үед `/report` 200-400мс хүлээдэг тул зогсолтын 1 секундэд хэвийнээс олон хүсэлт "багтдаг". Энэ зөрүүг Алхам 5-д бодитоор хэмжиж харна.

## Алхам 4: SLO-г k6 threshold болгох

`slo-test.js` — гурван endpoint-ийг `name` tag-аар ялгаж, tag тус бүрд threshold тавьсан. SLO хүснэгтийн 3 босго дээр нэмээд, зааврын дагуу `/report`-д зориулж 4 дэх threshold нэмсэн:

```js
thresholds: {
  'http_req_duration{name:cart}': ['p(95)<20'],    // Performance SLO
  'http_req_failed{name:pay}': ['rate<0.08'],      // Reliability SLO
  'checks': ['rate>0.90'],                          // Availability SLO
  'http_req_duration{name:report}': ['p(95)<450'], // Нэмэлт: report endpoint (200-400мс sleep-той)
}
```

`/report`-ын 450мс босгыг мөн бодит хэмжилтээс гаргасан: серверийн код `sleep(200 + Math.random()*200)` буюу 200-400мс хооронд хариулдаг тул p95 ~390-400мс орчимд байх ёстой, 450 нь үүнээс арай дээгүүр, бодитой хэмжигдэхүйц утга.

**PASS үр дүн** (`k6 run slo-test.js 2>&1 | tee results/pass.txt`):

```
checks
✓ 'rate>0.90' rate=98.56%

http_req_duration{name:cart}
✓ 'p(95)<20' p(95)=956.64µs

http_req_duration{name:report}
✓ 'p(95)<450' p(95)=391.37ms

http_req_failed{name:pay}
✓ 'rate<0.08' rate=4.30%
```

## Алхам 5: Мини chaos — availability сценариогоо бодитоор турших

`slo-test.js`-ийн `duration`-г `'2m'` болгож ажиллуулаад, ажиллаж байх үед серверийг Ctrl+C-ээр зогсоож, ~10 секунд хүлээгээд дахин `node server.js` асаасан (`results/chaos.txt`).

### Threshold-ын үр дүн

```
checks
✗ 'rate>0.90' rate=84.80%

http_req_duration{name:cart}
✓ 'p(95)<20' p(95)=1.19ms

http_req_duration{name:report}
✓ 'p(95)<450' p(95)=390.02ms

http_req_failed{name:pay}
✗ 'rate<0.08' rate=17.94%
```

- **Availability threshold (`checks: rate>0.90`) FAIL болсон** — 84.80% (5733 checks-ээс 4862 амжилттай).
- **Reliability threshold (`http_req_failed{name:pay}: rate<0.08`) мөн FAIL болсон** — 17.94% (1911 pay хүсэлтээс 343 алдаатай).
- Cart болон report threshold хэвээр PASS үлдсэн — эдгээр нь зогсолтын гадна тогтмол хэвийн ажилласан.

`chaos.txt`-д зогсолтын үед `dial tcp 127.0.0.1:3000: connect: connection refused` алдаа 795 удаа бүртгэгдсэн (22:28:01-22:28:14, буюу ойролцоогоор 13-14 секунд), 3 endpoint-д ойролцоо тэнцүү хуваарилагдсан (cart 261, report 267, pay 267).

### Бодит availability (ХҮСЭЛТЭЭР тооцсон)

Бодит availability = амжилттай хүсэлт / нийт хүсэлт = 4862 / 5733 = **84.80%**.

Энэ нь Алхам 3-т тавьсан 90% SLO-г хангаагүй — error budget хэтэрсэн.

### Яагаад хэтэрсэн бэ — SLO хэт өөдрөг үү, зогсолт хэт удаан уу?

Хоёулаа хэсэгчлэн нөлөөлсөн:

1. **Зогсолт төлөвлөснөөс арай удаан болсон.** `connection refused` алдаа 22:28:01-22:28:14 хооронд, өөрөөр хэлбэл ~13-14 секунд үргэлжилсэн (Node процесс дахин асаж, порт сонсож эхлэхэд бага зэрэг цаг ордог тул зөвхөн "10 секунд хүлээх" гэснээс арай урт болсон). Цагаар тооцвол: 13с / 120с ≈ 10.8% зогсолт → цагийн availability ≈ 89.2%, энэ өөрөө 90% SLO-той аль хэдийн ойрхон (доогуур).
2. **Гэвч бодит хэмжсэн 84.80% нь 89.2%-аас ч доогуур** — учир нь k6-ийн `checks` ХҮСЭЛТЭЭР тооцогддог, ЦАГААР биш. Хэвийн үед нэг iteration ~1.3с үргэлжилдэг (`/report`-ын 200-400мс хүлээлт голлодог). Зогсолтын үед бүх хүсэлт агшин зуур (connection refused) буцдаг тул `/report`-ын хүлээлт алга болж, iteration хугацаа богиносч, VU-үүд илүү олон удаа дахин оролддог. Үр дүнд нь зогсолтын 13 секундэд, хэвийн 13 секундэд багтах хүсэлтээс хамаагүй илүү хүсэлт "багтаж", тэдгээр бүгд амжилтгүй болсон тул нийт хүсэлтийн дундаж availability цагийн тооцооноос доогуур гарсан. Товчоор: Алхам 3-т цагаар тооцсон 12 секундийн budget нь хугацааны нэгж бүр адилхан "жинтэй" гэж үздэг байсан бол бодит байдал дээр зогсолтын секунд бүр хэвийн секундээс илүү олон бүтэлгүй хүсэлт агуулж байгаа тул ХҮСЭЛТЭЭР тооцоход budget хамаагүй хурдан шавхагдсан.

### Reliability threshold яагаад мөн FAIL болсон вэ

`/pay`-ийн 343 алдаанаас 267 нь зогсолтын үеийн connection refused, үлдсэн ~76 нь серверийн built-in ~5% санамсаргүй алдаа (76/1644 ≈ 4.6%, хэвийн baseline-тай ойролцоо). Өөрөөр хэлбэл сервер унахад `/pay`-ийн хүсэлт БҮГД (connection refused-ээр) унадаг тул нэг availability-ийн эвдрэл `http_req_failed{name:pay}` метрикт мөн орж, availability ба reliability хоёр SLO-г зэрэг зөрчсөн — учир нь хоёр SLI ижил "энэ хүсэлт амжилттай юу" гэсэн дохиог ашиглаж байгаа. Эдгээрийг тусгаарлахын тулд `/pay`-ийн reliability метрикээс сүлжээний түвшний алдааг (жишээ нь `res.status === 0`, яг connection refused-ийг илэрхийлдэг) ялгаж хасаж, зөвхөн серверийн хариулсан 5xx хариултыг reliability-д, харин connection-level алдааг зөвхөн availability-д тоолж болно.

## Алхам 6: Threshold-оо зориуд эвдэх

`slo-test-fail.js` — `slo-test.js`-тэй ижил, зөвхөн `/report`-ын threshold `p(95)<450` → `p(95)<100` болгож хатууруулсан (сервер 200-400мс-ийн sleep-той тул 100мс хэзээ ч хүрэхгүй — энэ нь ямар ч машин дээр найдвартай FAIL өгнө). Сервер энгийн (хэвийн, унаагүй) байдалтай ажиллаж байхад ажиллуулсан:

```
bash -c 'set -o pipefail; k6 run slo-test-fail.js 2>&1 | tee results/fail.txt; echo "exit=$?" | tee -a results/fail.txt'
```

(`pipefail` шаардлагатай — эсвэл `$?` нь k6-ийн биш, `tee`-ийн exit status-ыг (0) буцаадаг.)

**Гаралт:**

```
checks
✓ 'rate>0.90' rate=98.28%

http_req_duration{name:cart}
✓ 'p(95)<20' p(95)=822.89µs

http_req_duration{name:report}
✗ 'p(95)<100' p(95)=389.52ms

http_req_failed{name:pay}
✓ 'rate<0.08' rate=5.15%
```

бусад 3 threshold (cart, pay, checks) хэвийн PASS хэвээр байсан — зөвхөн report threshold зориудаар эвдэрсэн. Гаралтын төгсгөлд:

```
time="2026-09-22T23:...+08:00" level=error msg="thresholds on metrics 'http_req_duration{name:report}' have been crossed"
exit=99
```

k6 threshold зөрчигдөхөд **exit code 99**-ээр гардаг (амжилттай PASS үед 0 гардаг). CI pipeline яг энэ exit code-оор build-ыг pass/fail болгодог тул threshold зөрчил автоматаар pipeline-ыг зогсоох боломжтой.

**Нэмэлт ажиглалт:** `/cart/add`-ыг адилхан хэмжээгээр хатууруулж `p(95)<50` болгосон ч энэ localhost дээр PASS хэвээр үлдэх байсан. Шалтгаан нь `/report` дотор `sleep(200 + Math.random()*200)` гэсэн ХАТУУ 200мс-ийн доод хязгаар кодлогдсон байдаг бол `/cart/add` ямар ч sleep, DB, гадаад дуудлагагүй тул хариу хугацаа millisecond-аас доогуур хэвээр байдаг — өөрөөр хэлбэл threshold зөвхөн бодит боловсруулалтын доод хязгаарыг давсан үед л найдвартай FAIL өгнө.

## Дүгнэлт

Сценарио → SLO → threshold энэ гурван шатны шилжилтэд хамгийн хэцүү байсан хэсэг бол Алхам 3-т SLO-гийн тоог зөв сонгох явдал байлаа: эхэндээ зааврын жишээ тоог (`p(95)<200`) шууд хуулбарласан боловч бодит хэмжилт хийхэд энэ нь `/cart/add`-ийн жинхэнэ p95 (~1мс)-аас 150-200 дахин сул, юу ч шалгахгүй утга болох нь тодорхой болсон. Үүнээс сургамж авч, threshold бүрийг эхлээд бодитоор хэмжиж, дараа нь тэр хэмжилт дээр нөөцтэй босго тавих аргачлал руу шилжсэн. Chaos тест (Алхам 5) миний availability сценариог зарим талаараа батлав, зарим талаараа үгүйсгэв: сценариондоо бичсэн "сервер унасны дараа шинэ хүсэлт шууд хэвийн ажиллаж эхэлнэ" гэсэн хэсэг үнэн болсон — сервер дахин асахад нэн даруй 200 OK эхэлсэн. Гэхдээ "2 минутад 90% availability" гэсэн тоон SLO батлагдаагүй, бодит availability ердөө 84.80% гарсан. Энэ ялгаа гарсан гол шалтгаан нь миний Алхам 3-т хийсэн error budget тооцоо (12 секунд) ЦАГААР бодогдсон байсан бол k6 бодит байдал дээр availability-г ХҮСЭЛТЭЭР хэмждэг явдал байв — сервер унасан үед хүсэлт бараг агшин зуур (connection refused) буцдаг тул зогсолтын секунд бүрт хэвийн секундээс хамаагүй олон хүсэлт багтаж, тэд бүгд амжилтгүй болсон. Мөн нэг чухал ажиглалт: сервер унахад `/pay` хүсэлт бүр унадаг тул нэг crash availability болон reliability гэсэн хоёр өөр SLO-г зэрэг зөрчсөн — эдгээр хоёр SLI бодит байдал дээр давхцаж болохыг харуулсан. Алхам 6-д threshold-оо санаатайгаар эвдэхэд k6 `exit=99` кодоор гарч, яг CI/CD дээр яаж quality gate ажилладгийг практикт харуулсан. Ерөнхийдөө энэ лаборатори надад чанарын шаардлагыг "бодит хэмжилт → тоон SLO → автомат threshold" гэсэн шугамаар шилжүүлэхэд хамгийн том эрсдэл бол тоог бодит орчиндоо баталгаажуулалгүй шууд бичих явдал гэдгийг ойлгуулсан.
