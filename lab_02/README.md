| VU | p90 | p95 | throughput | error rate | нийт хүсэлт |
|---|---|---|---|---|---|

Мөн `stages.js`-ээр (5→30→100→0 VU) нэгтгэсэн ramp тест хийж, ачаалал өсөх/буух үеийн ерөнхий зургийг ажиглав (`results/run-stages.txt`) — гэхдээ дээрх хүснэгтийн тоог 3 тусдаа ажиллуулалтаас авсан бөгөөд stages-ийн нэгтгэсэн summary-г ашиглаагүй.

**Ажиглалт:** 5 → 100 VU (20 дахин) хүртэл ачаалал өсөхөд p95 latency бараг өөрчлөгдөөгүй (233–236 ms орчимд тогтвортой), харин throughput ачааллын хэмжээтэй шугаман (7.6 → 151.7 req/s) өссөн. "Нэгж хэрэглэгчийн туршлага" муудаж эхэлсэн тодорхой цэг 100 VU хүртэл ажиглагдаагүй.

## Алхам 4: Thresholds — SLO-гоо кодоор шалгуулах

**SLO-гийн үндэслэл:** Алхам 2-т хэмжсэн BASELINE p95 = 235.1 ms. Зааврын жишээгээр (baseline × 1.5) SLO = 235.1 × 1.5 ≈ 352 ms → бүхэлд нь **350 ms** болгож тогтоов. Error rate SLO = < 1% (лекцийн POFOD-той нийцүүлсэн).

### PASS (`thresholds.js`, vus=30, duration=1m)

```js
thresholds: {
  http_req_duration: ['p(95)<350'],
  http_req_failed: ['rate<0.01'],
}
```

```
✓ 'p(95)<350' p(95)=233.45ms
✓ 'rate<0.01' rate=0.00%
```

### FAIL (`thresholds-fail.js`, санаатайгаар хэт хатуу `p(95)<50`)

```
✗ 'p(95)<50' p(95)=231.66ms
time="2026-09-15T21:28:12+08:00" level=error msg="thresholds on metrics 'http_req_duration' have been crossed"
```

k6 threshold зөрчигдөхөд алдааны мессеж хэвлээд, процесс алдаатай (non-zero) кодоор гардаг — яг ийм зарчмаар CI pipeline дээр quality gate ажиллаж, build-ыг блоклодог.

## Дүгнэлт

Ачаалал 5 VU-с 100 VU (20 дахин) хүртэл өсөхөд `test.k6.io` сайтын p95 latency бараг өөрчлөгдөөгүй (235 ms орчимд тогтвортой байсан) бөгөөд throughput ачааллын хэмжээтэй шууд пропорциональ (7.6 → 151.7 req/s) өссөн, error rate 0% хэвээр байв. Энэ нь лекц 2-т үзсэн "10 хэрэглэгчид 2с, 100 хэрэглэгчид 4с" гэсэн классик latency-throughput зөрчлийг энэ тест дээр шууд ажиглаагүй гэсэн үг — учир нь `test.k6.io` бол CDN дээр байрлах статик (хөнгөн) демо сайт тул 100 VU хүртэлх ачаалал түүний хүчин чадлыг хангаж, даваагүй. Гэхдээ энэ нь чухал ойлголтыг баталсан: систем өөрийн хүчин чадлын хязгаараас доогуур ачаалалтай үед latency тогтвортой хэвээр байдаг бол, зөвхөн тухайн системийн хязгаарт ойртсон үед л доголдож эхэлдэг. Throughput нь VU тоотой шугаман хамааралтай өссөн нь сервер энэ түвшинд bottleneck болоогүйг харуулж байна. Threshold (SLO) хэсэгт p95<350ms гэсэн бодит baseline дээр суурилсан gate нийтдээ хангагдсан (PASS), харин санаатайгаар хэт хатуу (p95<50ms) threshold тавихад k6 автоматаар FAIL болгож, CI/CD дэх quality gate-ийн зарчмыг практикт харуулсан. Хэрэв энэ туршилтыг илүү "хүнд" backend (жишээ нь өөрийн локал сервер дээр sleep(100ms) endpoint) дээр давтвал, лекцийн жишээнд байсан шиг latency огцом нэмэгдэх магадлалтай — учир нь тухайн тохиолдолд серверийн боловсруулах чадвар илүү хурдан хязгаарлагддаг. Тодорхойлсон SLO (p95<350ms, error rate<1%) энэ орчинд бүрэн хангагдсан тул системийг энэ ачааллын хүрээнд найдвартай гэж дүгнэж болно.
